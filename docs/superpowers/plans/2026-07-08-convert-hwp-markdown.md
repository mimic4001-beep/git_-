# HWP 문서의 Markdown 변환 계획

- 작성일: 2026-07-08
- 대상 저장소: `mimic4001-beep/git_-`
- 관련 설정: 저장소 루트 `.mcp.json` (프로젝트 스코프 MCP 서버 `hwp-mcp`)
- 문서 성격: 실행 계획서(Implementation Plan)

---

## 1. 배경 및 문제점

국내 공공기관·연구기관의 보고서, 정책자료, 연구용역 산출물은 상당 부분 HWP 계열 포맷으로 유통됨. 그러나 후속 활용 환경은 텍스트 기반 포맷을 전제로 하고 있어 포맷 간 불일치가 발생함.

구체적 문제점은 다음 네 가지로 정리됨.

1. **버전관리 불가**: `.hwp`는 한컴의 독자 바이너리 포맷이므로 Git에서 diff·blame·merge가 성립하지 않음. 변경 이력 추적이 파일 단위 교체로 퇴행함.
2. **검색·색인 제약**: 바이너리 본문은 `grep` 등 일반 텍스트 도구로 탐색되지 않아, 저장소 내 전문 검색이 불가능함.
3. **구조 손실**: 수작업으로 복사·붙여넣기 변환 시 표의 병합 셀, 각주·미주, 수식, 이미지 참조 관계가 체계적으로 유실됨.
4. **파이프라인 단절**: RAG·LLM 처리, 정적 사이트 배포, 문서 품질 자동검사 등 후속 공정이 모두 Markdown/텍스트를 입력 전제로 하므로, 변환 단계가 병목으로 작용함.

따라서 HWP 원본을 **재현 가능한 절차로 Markdown화**하는 표준 변환 경로 확립이 선결 과제로 분석됨.

## 2. 현황

### 2.1 저장소 현황

현재 저장소는 커밋 2건 규모의 초기 상태이며, `.mcp.json`을 통해 `hwp-mcp` 서버가 프로젝트 스코프로 등록되어 있음. 변환 대상 문서와 산출물 디렉터리는 아직 존재하지 않음.

```json
{
  "mcpServers": {
    "hwp-mcp": { "command": "npx", "args": ["-y", "hwp-mcp"] }
  }
}
```

### 2.2 등록된 변환 수단의 기능 범위

`hwp-mcp`(npm)는 rhwp(Rust + WebAssembly 기반 HWP/HWPX 파서) 위에 구축된 MCP 서버로, Node.js 20 이상 환경에서 macOS·Windows·Linux를 지원하며 **한컴오피스 설치를 요구하지 않음**. 총 35개 도구를 노출함.

본 계획과 직접 관련되는 읽기·변환 계열 도구는 다음과 같음.

| 도구 | 기능 |
|---|---|
| `convert_hwp_markdown` | 문서 전체를 흐름 순서를 보존하여 Markdown으로 변환하고, 내장 이미지를 상대경로 링크로 내보냄 |
| `read_hwp` | 본문·표(Markdown)·이미지 목록을 통합 반환 |
| `read_hwp_text` | 본문에 머리말·꼬리말·각주·수식을 통합한 텍스트 반환 |
| `read_hwp_tables` | 병합 셀을 처리한 GFM 표로 반환 |
| `list_hwp_images` / `extract_hwp_images` | 내장 이미지 목록 조회 및 디스크 추출 |
| `get_hwp_info` / `get_hwp_page_def` | 문서 메타데이터·편집용지 정보 조회 |

즉, **변환 로직을 자체 구현할 필요가 없으며**, 기등록 서버의 `convert_hwp_markdown`을 1차 변환 엔진으로 삼는 것이 합리적으로 분석됨.

### 2.3 포맷 지원 범위

| 연산 | `.hwp` | `.hwpx` |
|---|:---:|:---:|
| 읽기 | 지원 | 지원 |
| 쓰기 | 미지원 | 지원 |
| SVG 렌더링 | 지원 | 지원 |

본 계획은 **읽기 전용 경로**만 사용하므로 `.hwp`와 `.hwpx` 모두 대상에 포함 가능함.

### 2.4 명시된 한계

공개 문서상 확인되는 한계는 다음과 같으며, 이는 후처리·검증 단계 설계의 근거가 됨.

- 검색 문자열이 복수 XML 텍스트 노드에 걸치는 경우 매칭되지 않음.
- 텍스트박스 내용 추출, 미주, 차트 지원은 v0.3으로 이연됨.
- 쓰기는 `.hwpx` 한정이며 교차 포맷 저장이 차단됨(본 계획에서는 비해당).

### 2.5 대안 스택 비교

`hwp-mcp` 경로가 실패하거나 결과 품질이 기준에 미달할 경우를 대비한 폴백 후보는 다음과 같이 정리됨.

| 스택 | 언어 | 특징 | 본 계획에서의 위치 |
|---|---|---|---|
| `pyhwp` (`hwp5txt`) | Python | HWP 5.0 바이너리 직접 해석, CLI 제공. 단, 표 텍스트가 셀 구조 없이 평면 출력됨 | 최후 폴백(텍스트만 필요한 경우) |
| `python-hwpx` | Python | OWPML(KS X 6101) 기반 HWPX 열기·편집·생성·검증 | HWPX 구조 정밀 검증용 |
| `hwp-hwpx-parser` | Python | 순수 Python, JVM 불요. 텍스트/표/각주/미주/메모 추출 | 미주 누락 보완용 |
| `syhwp` | Python | `.hwp`/`.hwpx` → 텍스트·Markdown·HTML. RAG 파이프라인 지향 | 1차 폴백(Markdown 교차검증) |

## 3. 연구방향

### 3.1 설계 원칙

- **무손실 우선**: 원본 `.hwp`/`.hwpx`는 저장소에 그대로 보존하고, Markdown은 파생 산출물로 취급함. 변환은 언제든 원본에서 재실행 가능해야 함.
- **구조 보존**: 표는 GFM 표로, 각주는 각주 표기로, 이미지는 상대경로 링크로 보존함. 평면 텍스트화는 허용하지 않음.
- **재현 가능성**: 변환 절차는 문서화된 명령 또는 스크립트로 고정하고, 동일 입력에 대해 동일 출력을 보장함.
- **검증 내장**: 변환 결과는 자동 점검 항목을 통과해야 병합함. 육안 확인에만 의존하지 않음.

### 3.2 산출물 정의

| 구분 | 경로 | 내용 |
|---|---|---|
| 원본 | `docs/source/*.hwp(x)` | 변환 대상 원본. 수정하지 않음 |
| 변환물 | `docs/markdown/<문서명>.md` | Markdown 본문 |
| 이미지 | `docs/markdown/assets/<문서명>/` | 추출된 내장 이미지 |
| 변환 로그 | `docs/markdown/_reports/<문서명>.json` | 변환 일시, 도구 버전, 경고 목록 |

### 3.3 수용 기준

변환 결과는 아래 기준을 모두 충족할 때 완료로 판정함.

1. 본문 문단 수가 원본 대비 누락 없이 대응됨.
2. 모든 표가 GFM 표로 렌더링되며, 병합 셀로 인한 열 수 불일치가 없음.
3. 내장 이미지 개수와 Markdown 내 이미지 링크 개수가 일치하고, 모든 링크가 실제 파일을 가리킴.
4. 각주·수식이 소실되지 않음. 미주·텍스트박스는 현 버전 한계로 **누락 가능성을 로그에 명시**함.
5. 결과 파일이 UTF-8, LF 개행으로 저장됨.

## 4. 연구방법

### 4.0 단계 0 — 전제조건 확인

- Node.js 20 이상 설치 여부 확인: `node -v`
- MCP 서버 연결 확인: `claude mcp list` 결과에서 `hwp-mcp` 항목이 `✓ Connected`로 표시되는지 점검함.
- 도구 시그니처 확인: 각 도구의 실제 파라미터명은 런타임 스키마(`/mcp`)에서 확인 후 사용함. 본 문서는 도구명 기준으로만 기술함.

### 4.1 단계 1 — 인벤토리 작성

변환 대상 문서를 수집하여 목록화함. 문서별로 포맷(`.hwp`/`.hwpx`), 용량, 페이지 수, 표·이미지 포함 여부를 기록하여 난이도를 사전 분류함. `get_hwp_info`, `get_hwp_page_def`, `list_hwp_images`를 사용함.

### 4.2 단계 2 — 단건 변환 파일럿

표와 이미지를 모두 포함한 대표 문서 1건을 선정하여 `convert_hwp_markdown`을 실행함. 이 단계의 목적은 대량 변환 이전에 **품질 기준의 현실성을 검증**하는 데 있음. 동일 문서에 대해 `read_hwp_tables`를 별도 실행하여 표 변환 결과를 교차 확인함.

### 4.3 단계 3 — 후처리 정규화

1차 변환 결과에 대해 다음 정규화를 적용함.

- 제목 계층 정리: 원본의 개요 번호(예: `1.`, `가.`, `1)`)를 Markdown 헤딩 수준으로 사상함.
- 공백·개행 정규화: 연속 빈 줄 축약, 전각 공백 제거, 행말 공백 제거.
- 이미지 경로 재작성: 추출 경로를 `assets/<문서명>/` 규칙으로 통일함.
- 표 정렬 보정: 열 수가 불일치하는 표를 탐지하여 보고함.

후처리는 별도 스크립트로 분리하여, 원본 변환 결과와 정규화 결과를 구분 가능하게 유지함.

### 4.4 단계 4 — 검증

3.3의 수용 기준을 자동 점검하는 검증 스크립트를 작성함. 점검 항목은 표 열 수 일치, 이미지 링크 유효성, 인코딩·개행, 헤딩 계층 연속성으로 구성됨. 불합격 항목은 변환 로그에 경고로 기록하고 수동 검토 대상으로 분류함.

### 4.5 단계 5 — 배치 자동화

파일럿 결과가 수용 기준을 통과하면 인벤토리 전체에 대해 변환을 반복 실행함. 실패 문서는 중단 없이 건너뛰고 로그에 사유를 남기며, 폴백 스택(2.5) 적용 대상으로 분류함.

### 4.6 폴백 경로

| 증상 | 대응 |
|---|---|
| 서버 미연결 / Node 버전 미달 | Node 20+ 설치 후 재시도. 미해결 시 `syhwp` 경로로 전환함 |
| 표가 평면 텍스트로 출력됨 | `read_hwp_tables` 결과로 해당 표 구간만 치환함 |
| 미주·텍스트박스 누락 | `hwp-hwpx-parser`로 해당 요소만 추출하여 보완함 |
| 특정 문서 파싱 실패 | 원본을 `.hwpx`로 저장 후 재시도. 미해결 시 수동 처리 목록으로 이관함 |

## 5. 적용

### 5.1 실행 순서

1. 전제조건 확인(4.0) — 반나절
2. 대상 문서 수집 및 인벤토리 작성(4.1) — 문서 규모에 비례
3. 파일럿 1건 변환 및 기준 조정(4.2~4.3) — 1일
4. 검증 스크립트 작성(4.4) — 1일
5. 전체 배치 변환 및 예외 처리(4.5) — 문서 규모에 비례

### 5.2 디렉터리 구성

```
docs/
├─ source/                  # 원본 HWP/HWPX (수정 금지)
├─ markdown/
│  ├─ assets/<문서명>/      # 추출 이미지
│  ├─ _reports/<문서명>.json
│  └─ <문서명>.md
└─ superpowers/plans/       # 본 계획 문서
```

### 5.3 위험요인 및 대응

| 위험요인 | 영향 | 대응 |
|---|---|---|
| `npx -y` 기반 실행으로 인한 버전 변동 | 재현성 저하 | 변환 로그에 실행 시점 패키지 버전을 기록하고, 필요 시 `.mcp.json`에서 버전을 고정함 |
| 원본 문서의 저작권·비공개 자료 포함 | 공개 저장소 유출 | 공개 가능 여부를 사전 확인하고, 비공개 문서는 `.gitignore` 처리 또는 별도 비공개 저장소로 분리함 |
| 도구 한계로 인한 요소 누락(미주·차트) | 내용 결손 | 변환 로그에 누락 가능 요소를 명시하고, 해당 문서는 수동 검토 대상으로 표기함 |
| 대용량 이미지 다수 포함 | 저장소 비대화 | 이미지 용량 상한을 정하고, 초과 시 외부 스토리지 링크로 전환함 |

### 5.4 확인이 필요한 사항

본 계획을 실행 단계로 전환하기 위해서는 다음 사항의 확정이 필요함.

1. 변환 대상 문서의 소재와 수량 — 현재 저장소에는 대상 파일이 존재하지 않음.
2. 원본 포맷 구성 — `.hwp`와 `.hwpx`의 비중.
3. 원본 문서의 저장소 커밋 가능 여부(공개·비공개 판단).
4. 이미지 처리 방침 — 저장소 내 포함 여부 및 용량 상한.

## 6. 결론

본 계획을 통해 다음이 도출됨.

- HWP 계열 문서의 Markdown 변환은 **자체 파서 구현 없이**, 이미 저장소에 등록된 `hwp-mcp`의 `convert_hwp_markdown` 도구를 1차 엔진으로 삼아 해결 가능함으로 분석됨.
- 해당 도구는 한컴오피스 설치를 요구하지 않고 `.hwp`·`.hwpx` 읽기를 모두 지원하므로, 운영체제 제약 없이 변환 파이프라인을 구성할 수 있음으로 분석됨.
- 다만 미주·텍스트박스·차트는 현 버전에서 지원되지 않으므로, 무조건적 자동화가 아니라 **검증 단계와 폴백 스택을 병행하는 이중 구조**가 필요함으로 도출됨.
- 원본 보존, 구조 보존, 재현 가능성, 검증 내장의 4원칙과 5단계 실행 절차, 4개 수용 기준을 본 변환 작업의 표준 절차로 설정함.
